# 一句话出 HTML 原型

## 什么时候用
- 评审、演示前需要一个能点的页面；用户只有一句话或几行需求。

## 什么时候不用
- 要能上线的生产代码（接口、权限、构建）→ 本 Skill 只出演示原型。
- 要改设计稿文件 → 不适用。
- 只要交互说明文字 → 直接写说明。

## 第 1 步：3 行复述 + 假设（停下确认）
用 3 行写：**谁用 / 在这个页面完成什么 / 完成的标志是什么**。再列「我的假设」（最多 5 条，例如「假设列表每页 20 条」「假设删除需要二次确认」），然后停下等用户确认或修改。
- 用户说「直接出」，就按假设出，并把假设写进页面底部的「本原型的假设」区块。

反例：用户说「做个订单管理」，你直接出了 8 个页面、带登录和权限。→ 范围膨胀。一句话需求默认只出 **1 个主页面 + 必要的弹层**。

## 第 2 步：选页面类型、读规矩
读 `reference/页面规矩.md`，判断是列表页、表单页、详情页还是看板页，按对应规矩出。

## 第 3 步：基于骨架出页
复制 `templates/skeleton.html`，在它上面改，不从空白开始：
- **单文件**：样式和脚本都写在这一个文件里，不引用任何外部链接、字体、图片，离线双击能打开。
- 颜色、间距只用骨架里的 CSS 变量，不在元素上写死颜色。
- 示例数据 5–8 条，字段要像真的（订单号、金额、状态），但全部标「示例」，不用真实公司名和人名。
- 必须能演示的状态：有数据 / 空状态 / 操作失败提示 / 危险操作二次确认。骨架里的「状态切换」小条保留，方便演示时切换。
- 详情一律用右侧抽屉，不用居中弹窗挤满屏幕。

## 第 4 步：7 条交互自检（逐条写结果）
在回复里列出这 7 条，每条写「通过」或「不通过 → 怎么改的」：
1. 核心操作线上步骤 ≤ 线下
2. 输入方向 = 用户脑子里想的（想「收 4300」就让他填 4300，不让他填差额）
3. 系统能给的选项用选择，不让手填
4. 没有需要用户心算的地方
5. 高频选项有默认值
6. 改了 A，关联的 B 自动更新
7. 核心操作 ≤ 3 步

## 交付
1. HTML 文件（或完整代码块，文件名用英文短名，如 `order-list.html`）。
2. 7 条自检结果。
3. 「本原型的假设」清单，提醒用户评审时逐条确认。
